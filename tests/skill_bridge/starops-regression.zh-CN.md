# alibabacloud-ros-agent：StarOps 回归测试清单

更新日期：2026-10-12。本文是可复用的测试规程，不是本轮测试通过报告；编写本文不启动测试。

## 1. 目的与范围

验证 StarOps Agent 使用 `alibabacloud-ros-agent` 技能，经真实 remote `aliyun` 执行器调用 `ros.aliyuncs.com` 的完整链路，重点覆盖交互续接、HIL 生命周期、模板与工件一致性及受控资源操作。

回归包含 **7 个有效业务场景组：S01～S06、S08**。S07 私有 OSS 上传与预签名链接交付已按用户要求移除，不执行、不计入验收或发布门槛；保留编号以便关联历史记录，不把历史失败改记为通过。不再把每个检查点拆成独立会话。允许复用场景中的任务验证多个检查点；允许/拒绝等互斥分支仍需分别执行并记录。断连等不可稳定触发的异常放入独立故障注入矩阵，不冒充真实平台覆盖。

三个测试层次必须分别报告：

| 层次 | 执行环境 | 能证明什么 |
| --- | --- | --- |
| 本地离线回归 | pytest、假执行器、隔离状态目录，无真实云调用 | 确定性边界、解析、生命周期及安全策略符合预期 |
| StarOps 真实 E2E | 真实平台、真实 remote CLI、ROS 线上 | 实际业务及平台交互链路可用 |
| 隔离故障注入 | 线程内技能副本、假 CLI 或受控中断 | 特定故障分支已执行；不证明真实平台必然按相同方式失败 |

非 remote 的 code/local CLI 不在 StarOps 本轮主线内，修改共享代码时仍需本地防回归。超过 32KB 的大模板完整传输专项不作为本轮重点；资源创建成功不能依赖 LLM 工具结果能展示大模板。

## 2. 执行前准备与安全边界

### 2.1 冻结版本与配置

每轮先记录代码提交及是否包含未提交修改、ZIP SHA256、安装后的脚本 SHA256、测试日期和配置。不要沿用上轮包名或旧哈希推断本轮版本。

基线 `config.json` 位于安装技能根目录，与 `SKILL.md` 同级：

```json
{
  "transport": "aliyun_cli",
  "aliyunCLIExecutionMode": "remote",
  "allowedAgentModes": ["normal"],
  "managerIdleSeconds": 60,
  "enableThinking": true,
  "aliyunCLIForwardEnv": ["STAROPS_HIL"],
  "debug": false
}
```

预期有效 endpoint 为 `ros.aliyuncs.com`；未显式配置时使用技能默认值。remote 模式不配置本地 Profile，不更改 AK、CLI current profile 或平台权限策略。无需设置 `ALICLOUD_ROS_AGENT_EXECUTOR_VERSION`、`ALICLOUD_ROS_AGENT_EXECUTOR_CAPABILITIES`。

执行 `check`，确认执行器存在、transport/mode/endpoint 与预期一致。`startChatReconnectReady` 为 false 时停止并记录阻塞原因；remote check 成功不证明真实鉴权和重连已经通过，仍以运行结果为准。

pipeline 场景需要安装管理员/用户事先授权，在当前线程创建技能副本，仅将副本的 `allowedAgentModes` 改为 `["normal", "pipeline"]`，使用独立 `ALICLOUD_ROS_AGENT_STATE_DIR`。每次副本命令沿用该状态目录；不修改全局技能、不切换 transport，不用修改白名单绕过业务任务中的限制。

`SKILL.md` 按 UTF-8 字节检查平台 32KB 上限，不能用字符数代替。更新/删除平台技能、上传 ZIP、执行云操作均以当轮用户授权为准；本文和历史测试授权不自动授权未来的操作。

无当前请求 SSE 游标的追问恢复支持由在线服务同学推进，执行前确认实际发布契约及技能适配版本。此前本地的只读 checkpoint 探测候选方案已撤除；当前技能在无锚点断连时报告结果未知，不使用额外 API 探测、不重发答案。冷权限恢复后的执行权交接、工件元数据更新修复需发布云端 iac-code。只更新技能 ZIP 不能替代相关服务端发布；未上线时分别记录依赖，不能宣称真实恢复通过。

### 2.2 公共执行规则

- StarOps 真实 E2E 禁止替换为假 CLI。外层 Agent 不得自行生成模板或模拟 ROS 追问冒充成功。
- 提示词和回答文件使用 UTF-8，保存在当前线程工作区。从该工作区执行桥接脚本，脚本使用绝对路径；不要进入技能目录执行，或把提示词放进技能目录。
- remote CLI 命令保持前台运行，不使用 `&`、`nohup` 或并行 follow 维持 HIL。平台工具超时必须覆盖权限等待和执行；技能不能延长宿主强制超时。
- 每次 foreground 调用转发当前 `STAROPS_HIL`；转发不等于刷新/延长宿主令牌，不读取、打印或持久化其值。
- 保持同一任务的 `jobId` 和最新返回的观察 `cursor`。观察 cursor 与服务器 SSE 恢复事件 ID 不是同一个概念，不能互相代替或自行推算。
- `follow` 只观察；`continue` 发送真实业务消息/回答，不能用于催促、轮询或“卡住重试”。只有明确取消时才执行 `cancel`。
- 对外及时展示进展、问题、权限动作及最终结果；不能只留下思考文本或工具 JSON。
- 不因断连、观察超时或父命令结束而自动重发 Query、新建替代任务或执行 StopChat。
- S01～S06 默认不创建/修改/删除云资源；S07 已移除，不再发起 OSS 上传或生成预签名链接。云资源写操作仅在 S08 的当轮明确授权范围内执行。

### 2.3 两层权限不能混淆

| 类型 | 来源与识别方式 | 回答方式 |
| --- | --- | --- |
| 平台 CLI 调用确认 | StarOps 执行器在执行 `aliyun` 时发起 | 平台确认交互；不算 ROS `permission` 覆盖 |
| ROS `permission` | 桥接返回真实 `inputRequired.kind=permission` 或待处理权限集合 | 同一 job 使用 `respond --decision allow_once/deny`；多条权限使用返回的 `permissionRef` |
| ROS `ask_user_question` | 桥接返回真实 `kind=ask_user_question` | 同一 job 使用 `continue` 发送用户回答 |
| ROS `candidate_selection` | 桥接返回真实 `kind=candidate_selection` | 经授权选择时，`continue` 的提示文件只写返回的候选 `options[].id`；不以 `respond` 回答 |

普通文本“请问……”或外层 Agent 自己弹出的问答，不证明 ROS 产生了结构化事件。权限关联字段由桥接管理，不手工重建权限 JSON、不猜 inputId；诊断记录可以引用已返回的非秘密标识，但不能修改它们来发起调用。

## 3. 七个有效真实场景组与保留编号

下列提示词是测试输入，不保证 LLM 每次产生相同事件。未实际触发的分支必须标记“未覆盖”，不能反复更改断言直到看起来通过。

### S01：基础模板、参数、多行输入与会话隔离

模式：normal；只生成，不部署。

参考提示词：

```text
/alibabacloud-ros-agent 请通过 ROS Agent 生成 ROS YAML 模板，不创建任何云资源。
要求：一个 VPC、两个交换机；VPC 网段 192.168.0.0/16，两个交换机分别为
192.168.1.0/24 和 192.168.2.0/24。参数包含 ZoneId 和名称前缀，Outputs 返回
VPCId 和两个 VSwitchId。不需要 ECS、NAT、EIP 或其他资源。
请返回完整模板正文与可获取的模板文件。
```

操作与验收：

- 输入包含中文、实际换行和末尾换行；可加入一小段多行 YAML 约束，确认 remote CLI 不因命令中的换行报错。
- 检查资源清单、网段、参数、Outputs 与要求一致；原提示文件不被改写。remote 换行会被规范化为空格，不要求保留 Query 中的 YAML 原始排版。
- 等到权威 `turn-completed`/最终结果，不把“已启动”或心跳当完成。
- 实际保存模板，检查字节数及 SHA256；如返回工件哈希，核对一致性。
- 可并行准备另一独立 StarOps 会话，以不同名称前缀或网段生成模板，验证结果及文件不串用。不要在同一 job 上并行 follow。
- `debug=false` 时本轮不新增 debug JSONL；旧日志存在不能判定 debug 仍开启。

### S02：同一会话连续修改与最新工件

模式：normal；复用 S01 的 job/session。

参考后续消息：

```text
继续使用同一个 ROS Agent 会话，将名称前缀改为 ros-regression-v2，
保留原网段和资源数量。只修改模板，不部署；返回更新后的完整正文及文件。
```

```text
仍在同一会话，将第二个交换机网段改为 192.168.3.0/24，保留上一次名称修改。
不要部署；再次返回更新后的正文及文件。
```

验收：

- 两次使用同一 job/session 的 `continue`，不重新 start；按实际协议记录 turn/task 变化，不要求所有 taskId 永远相同。
- 最后模板同时包含两次修改，第一交换机及其他约束没有意外变化。
- 最新文件内容、返回工件的字节数/哈希对应当前版本，不把旧工件当新结果。
- 如果正文正确但工件元数据仍旧，分别记录内容与元数据结果；若依赖的云端修复尚未上线，标记阻塞及依赖版本。

### S03：连续真实追问与候选选择

模式：pipeline，使用隔离副本；不选择部署。

参考提示词：

```text
/alibabacloud-ros-agent 请通过真实 ROS Agent pipeline 做需求澄清。
我有一个项目想在阿里云上线，请先用 ask_user_question 询问应用类型：
静态网站或 API 后端；收到答案后，再单独询问部署环境：开发测试或生产。
请等待我逐题回答，不要由外层 Agent 代选。之后展示方案供检查，
不要创建资源、购买服务或执行部署；若到候选选择边界，先停下展示候选。
```

操作与验收：

1. 收到第一个真实 `ask_user_question` 后，展示原问题及全部选项；回答“静态网站”。
2. 同一 job 发送回答，等到第二个不同的真实问题；回答“开发/测试”，也可用等价自由文本验证自由输入。
3. 两次回答均成功续接，无输入覆盖、旧问题重复或替代 job。
4. 如果返回 `candidate_selection`，记录真实 kind、候选及关联标识；不选择、不部署。此项只证明到达候选边界，不证明完整 pipeline 完成。
5. 若返回的是普通文本追问，仅记录文本流程结果；结构化问题覆盖仍为“未覆盖”。
6. 若回答后发生无当前请求锚点的 SSE 断连，预期报告 `missing_recovery_anchor` 和结果未知；即使已知 SessionId 和上一轮游标，也不使用旧游标续接当前请求、不调用额外探测 API、不重发答案或创建替代 job。记录为真实恢复阻塞，不视为业务流程通过。已有当前请求有效锚点时，仍验证同一请求的正常重连。

### S04：真实 ROS permission 的允许、拒绝与延迟

模式：以实际能触发 ROS 权限的 normal/pipeline 路径为准；使用无云资源副作用的动作。互斥分支分别执行。

参考提示词：

```text
/alibabacloud-ros-agent 请让 ROS Agent 在它自己的工作目录执行一次受控 Bash：
创建只包含 hello-regression 的临时文本文件，再读取该文件。
不修改既有文件、不访问凭证、不调用云资源写 API。
如果 ROS 产生工具权限请求，请展示原始动作等待我决定，不要自动批准。
```

分支与验收：

- 允许一次：必须收到真实 ROS `permission`，用 `respond allow_once` 回答，验证动作执行且原任务继续。
- 拒绝：用 `respond deny` 回答，验证被拒绝动作未执行，不由外层 Agent 替代执行；不硬性要求任务最终只能是 failed，云端可以正常结束并解释拒绝。
- 冷恢复后下一轮：权限等待期间原云端进程退出后，在恢复进程中回答允许或拒绝；等本轮正常结束，再以同一 session 发起只读新轮，验证无执行权冲突。普通热续接不能冒充冷恢复；无法稳定触发时以本地进程重启测试单独覆盖。
- 重复答案：仅在隔离故障注入中重复同一已完成的权限答复，验证返回已记录回执、工具不重复执行，也不重新占用执行权；真实平台不为造覆盖而重复授权。
- 延迟：从首次观察到 ROS 权限请求开始计时，至少 120 秒后回答；检查等待、reader 交接及后续续接。
- 有明确 `permissionAck` 时检查 `accepted`；串行恢复路径也可能直接返回下一输入/最终结果，按当前协议验收，不能要求每条路径都必须有 ack。
- 若出现多个权限，分别处理，保持父任务；记录实际 permissionClass。未触发的 normal/pipeline/sub_pipeline 类不能宣称全覆盖。
- 若同一业务任务出现“追问 → 权限 → 下一追问”，附带验证混合输入路由；无法触发时留作条件覆盖，不伪造事件。

平台 CLI 的 yes 弹窗不能替代以上任何一项。

### S05：平台延迟确认与 HIL 生命周期

穿插在 S01～S04 的真实调用中，不必另开完整业务场景。

操作：

- 对实际触发平台 CLI 权限确认的 start、follow、continue/respond 分别记录。
- 从首次看见弹窗开始，至少等待 120 秒后才确认；没有弹窗的命令标记“不适用/未触发”，不得伪造等待。
- 另做一次平台拒绝分支，使用无资源副作用任务，不与 ROS permission 拒绝混为一项。

验收：

- 权限等待期间活跃 foreground 不因 60 秒 manager 空闲配置或观察窗口提前退出。
- 确认后原任务正常续接；不并行发起 follow 保活、不依赖后台进程的旧 HIL。
- 后续新 foreground 命令正常获得当前上下文；不读取令牌值证明刷新。
- 宿主强制超时、用户关闭命令与技能空闲退出分开归因。HIL 真正过期时如实报错，不盲目重发。
- 分别记录权限等待时间与确认后的执行时间，避免将人为等待算成服务端慢。

### S06：长任务、等待后恢复与主动取消

使用纯生成或受控本地长任务，不在创建云资源过程中注入中断。

参考提示词：

```text
/alibabacloud-ros-agent 请让 ROS Agent 执行一个无云资源副作用的长任务：
在自己的 Bash 中输出 phase-1，等待 75 秒，输出 phase-2，再等待 75 秒，
输出 phase-3。不访问凭证、不修改既有文件。权限请求先展示给我决定。
```

操作与验收：

- 长任务超过 manager 空闲时间及常规观察窗口；忙碌时不能按空闲退出。不要把缓冲输出期间没看到增量误判为任务没运行。
- 一个 remote start foreground 活跃期间不额外 follow，也应能继续；外层命令返回后再按返回状态决定下一步。
- 在真实等待输入边界暂不回答/不 follow，超过空闲时间后再回答；管理服务可恢复并继续原任务，不靠永久后台保活。
- 另开无副作用长任务，明确要求“取消当前任务”，检查 `cancel` 的真实结果；Stopping 继续观察，NoActiveStream 如实报告，不一律声称已取消成功。
- 若测试 foreground 中断，只中断本轮任务。恢复仅使用当前请求已提交的 SessionId/SSE 事件锚点，不重复原业务消息。
- 不能只凭 PID 变化推断云任务重启/结束；缺少进程诊断时以可观察行为及桥接结果验收。

### S07：已移除（原私有 OSS 临时链接交付）

2026-10-12 按用户要求移除。停止该场景的上传、签名链接交付、扩展诊断与专项修复，不作为 S08 或发布验收的前置条件。历史执行证据保留在各轮报告中，状态记为“已移除/不纳入验收”，不记为通过。S01/S02 的模板与工件一致性、S04 的正常权限允许/拒绝验证仍保留，不要求通过 OSS 交付来完成这些检查。

### S08：VPC＋两个交换机创建、查询、修改和清理

最后执行。前置是当轮明确授权及关键交互回归没有阻塞；本文不自动授权创建或删除。

默认建议范围：测试账号、`cn-hangzhou`、独立 VPC＋两个交换机，不创建 ECS、NAT、EIP 等额外资源。可用区、唯一名称/测试标签及资源清单在执行前确认，不假定历史账号或可用区仍有效。

操作：

1. 先生成方案，展示架构图、参数、资源数量及影响，取得本轮执行确认。
2. 通过 ROS Agent 创建；记录 StackId 和本轮资源 ID，查询确认真实最终状态，不能仅凭模板生成或 Agent 宣称成功判定创建通过。
3. 查询网段、可用区、VPC 归属及资源数量；在同一 ROS 会话做一次名称/描述/标签等低风险修改。若 API 不支持目标字段，明确标记限制，不改网段或替换资源来凑覆盖。
4. 在授权范围内删除本轮栈/资源，并查询确认清理。只使用本轮已记录的精确 ID，不按宽泛名称/标签批量删除。

验收：

- 创建、查询、修改、清理分别记录真实状态和标识；没有混入额外收费资源或既有业务资源。
- 遇到断连或结果未知，先核对是否已创建，不重发创建消息。未知状态和残留资源显著列出，不宣称通过。
- 资源清理不等于 `cancel`：StopChat 不是删除资源或回滚栈的替代品。
- 外层不能绕过技能自行调用云写 API 来“修复”回归结果。

## 4. 独立故障注入矩阵

真实场景中自然触发时记录真实证据；否则仅在隔离副本/离线测试验证。假 CLI 注入和真实 CLI 结果必须明确区分。不要修改全局执行器、降低平台审批策略或在资源创建任务上故意断连。

| 编号 | 故障 | 预期行为 |
| --- | --- | --- |
| FI01 | 当前请求已提交恢复锚点后出现 SSE connection lost | 同一 SessionId 从最后已提交事件 ID 重连，不发送 Query，重放事件不重复展示 |
| FI02 | 首次请求在完整锚点之前断连 | 报告 missing_recovery_anchor、云端结果未知；不猜游标、不重发、不主动 StopChat |
| FI03 | 回答问题的新请求无锚点就断连 | 不借用旧游标、不重复回答；只读状态有同 session/task 的答案回执及新等待边界时恢复展示，否则结果未知；会话/任务/回执不匹配、权限边界、超大响应、接口不可用均不可推断恢复成功 |
| FI04 | JSON/数组被截断，但前面含完整事件与锚点 | 只保留完整事件，先提交检查点再补取；返回码为 0 也不能当业务完成 |
| FI05 | 截断发生在首个完整事件之前 | 不提交半条事件，不伪造 SessionId/恢复 ID，不自动再 start |
| FI06 | 连续断连但没有新事件进展 | 按当前实现的三次连续无进展中断上限停止；有新提交事件才重置预算，不无限补取 |
| FI07 | HIL 过期、鉴权失败、StreamExpired 或非法游标 | 保留原错误，不因含有连接错误字样误归类为可恢复 SSE 断连 |
| FI08 | 已收到完成/失败等权威终态，随后发生传输错误 | 终态优先，不将成功覆盖成传输失败，不重新执行任务 |

注入记录应包含故障点、输出形式（stderr/stdout/JSON 包装）、退出码、真实/假执行器、调用次数及 Query 是否只提交一次。不能为了取证记录 HIL、AK、完整私有历史或输入提示词到 debug 日志。
